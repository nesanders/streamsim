What we're testing and why

We're evaluating whether a language model running entirely inside your browser — on your CPU, with no internet connection to any AI service, no API key, no server — is fast and smart enough to power a conversational assistant for the StreamSim classroom tool.

Current model under test: SmolLM2-135M (135 million parameters, by Hugging Face). Our first choice, Qwen3-0.6B, crashed the WASM runtime with an out-of-memory error — its 4-bit weights are ~928 MB, exceeding WebAssembly's practical memory ceiling. SmolLM2-135M (~270 MB) is the smallest instruction-tuned model with a realistic chance of fitting. If even this model's quality is too low, the WASM-only approach is not viable and we will need to reconsider (WebGPU for on-device, or a free cloud API with a teacher-supplied key).

It runs via Transformers.js, which compiles the model to WebAssembly (WASM) so it executes on any modern browser, on any device, even without a GPU.

The three tests below mirror exactly what StreamSim's assistant would need to do in a real classroom session: answer a student's question about the simulation, generate a novel scenario as structured data, and decide which simulation parameter to change in response to a natural-language request (function calling).

Watch the tokens/sec and judge the response quality yourself. There's no automated pass/fail — you're the judge of whether it's good enough for classroom use.

Step 1 — Load the model

The model weights (~928 MB, 4-bit quantized) are downloaded from Hugging Face into browser memory. Because the file exceeds typical browser cache quotas, it is not persisted — it re-downloads on each page load. This is a known limitation being evaluated as part of this feasibility test.

On a slow school WiFi connection this download could take 3–8 minutes.

Test 1 Q&A — explain what's happening in the simulation

The most common student interaction: "Why does this service keep losing subscribers?" The model receives a snapshot of current sim state and must give a plain-English explanation appropriate for a high schooler. Quality matters more than speed here.

Test 2 Function calling — manipulate a simulation parameter

For direct sim control, the assistant must convert a natural-language request into a structured JSON tool call that our JavaScript can execute safely — no eval(), no free-form code. The model is given a tool schema and must pick the right function with valid arguments. This tests whether a 0.6B model can reliably produce parseable, correctly-typed JSON.

Test 3 Scenario generation — create a novel classroom scenario

Teachers can ask the assistant to invent a new simulation scenario — a named economic situation with specific parameter values and a pedagogical goal. The model must return a valid JSON object that our code can load directly. This is the hardest task for a small model: it requires creativity, domain knowledge, and strict structured output.

Reading the results

Tokens/sec: >8 tok/s feels fluid; 3–8 tok/s is usable but noticeable; <3 tok/s will frustrate students waiting for a response mid-class.

Function call (Test 2): The JSON must parse cleanly and have the correct field names and types. If it hallucinates a field name or outputs malformed JSON, the assistant cannot safely control the simulation — it would be limited to Q&A only.

Scenario JSON (Test 3): A creative, well-structured scenario suggests the model understood the domain. Gibberish or missing required fields means scenario generation would need a larger model or a cloud fallback.

Bottom line: If Tests 1 & 2 both pass at acceptable speed, we proceed with Transformers.js as the sole backend. If Test 2 fails repeatedly, we limit the assistant to Q&A and add a teacher-supplied API key option for sim control.
